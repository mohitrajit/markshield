5. Component or Module Walkthrough

5.1 verifier.py (Core Verification Library)

What it is: A pure-Python verification library (1,150 lines) implementing the Verifier class and verify_file API.
Why it was built: To perform high-speed, deterministic syntactic, structural, and security validation on Markdown documents without LLM dependencies.
How it works: Executes 10 inspection passes (BOM, front matter, headings, fences, tables, links, images, procedures, text hygiene, and legacy checks).
Inputs & Outputs: Takes document text or file path and configuration dictionary; outputs structured Issue objects (line, code, severity, message, impact, fix).
Configuration: Governed by learned rules from the master template and rule overrides from rules.yaml.

5.2 agent.py (Autonomous Daemon & Batch Runner)

What it is: Autonomous folder watcher and batch pipeline driver (545 lines).
Why it was built: To eliminate manual verification workflows, manage safe file routing, generate multi-tab Excel reports, and dispatch email alerts.
How it works: Periodically polls inbox/, enforces settle time buffers, coordinates file and asset moves, synthesizes openpyxl workbooks, and sends emails.
Inputs & Outputs: Watches inbox/; outputs to verified/, failed/, reports/, and dispatches SMTP emails.
Configuration: Reads parameters from .env (SMTP settings, POLL_SECONDS, SETTLE_SECONDS, directory paths).

5.3 rules.yaml (Configuration Overlay)

What it is: Declarative YAML configuration file (74 lines).
Why it was built: To define strict field regex patterns, enumerations, allowed HTML tags, and chunk thresholds that cannot be expressed in Markdown.
How it works: Overlays learned template fields via field_overrides; defines optional_keys, section_types regex mappings, and legacy cleanup lists.
Inputs & Outputs: Parsed by load_rules() and merged with template schema.

5.4 RAG-SAMPLE-MASTER-TEMPLATE.md (Golden Contract)

What it is: Authoritative master Markdown document (983 lines) demonstrating all valid documentation patterns.
Why it was built: Serves as the single source of truth from which verifier.py learns valid front matter keys, types, and canonical section orders.
How it works: Parsed at runtime by learn_template(); changes to this file immediately update validation expectations.

5.5 test_mutations.py (Mutation Test Suite)

What it is: Regression testing harness (106 lines) executing 46 programmatic template breakages.
Why it was built: To mathematically verify that every cataloged rule code is triggered when its corresponding defect is introduced.
How it works: Mutates RAG-SAMPLE-MASTER-TEMPLATE.md in temporary directories and verifies that expected error codes fire on expected lines.

5.6 .env / .env.example (Secrets Configuration)

What it is: Local environment files defining SMTP credentials and operational parameters.
Why it was built: To isolate sensitive credentials from version control while providing zero-dependency environment variable parsing.
